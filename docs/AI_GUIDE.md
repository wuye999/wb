# AI 日常操作指南

平台协议入口见 [开发指南](DEVELOPMENT.md#平台接口资料)；根目录 `api/` 是不随 Git 分发的维护者私有资料。先定位当前代码使用的端点；“抓包参考”和“外部参考”不代表已实现或获准调用，不因找到旧接口就切换生产通道。BCS 以现行请求结构为主，WB 后台会话与 WB Open API 令牌分开处理。

面向替用户执行运营任务的 AI。先阅读 [AGENTS.md](../AGENTS.md) 和本指南，再按 [USAGE](USAGE.md) 选择流程，参数以 [CLI](CLI.md) 为准。只有维护者明确授权的开发任务才进入 [开发准则](DEVELOPMENT.md)。

## 判断任务边界

1. 确认项目目录、Python 解释器和入口 run.py，命令与参数以当前 CLI 帮助为准。
2. 明确用户要求的是查询、报表、本地修改、远端提交还是长期自动运行，以及店铺、商品、日期、库存数量等范围。能从用户指令和已有数据明确推断的内容无需重复确认；会实质扩大范围且无法确定的内容需要先澄清。
3. 普通运营任务只允许运行已有命令、读写用户自己的 data，以及在 _scratch 写临时脚本。不得为了修报错或图省事修改源码、依赖、文档和项目配置；记录问题交维护者处理。
4. 数据目录默认与 run.py 同级。只有用户要求使用另一份数据时才覆盖路径；手动操作、备份与计划任务应使用同一个生产数据目录。

## 当前仓库与凭证约定

- 凡涉及仓库的操作，默认且仅允许目标店铺的莫斯科仓库 ID。全店、全部商品、库存清零或下架请求都不代表可以操作全仓；读取库存、生成计划和临时脚本也要限定莫斯科。
- 先用仓库列表核对该店莫斯科仓库名称和 `id`，不要把 office 字段 `warehouseId` 当作库存仓库 ID，不跨店复制 ID。找不到莫斯科或无法确认时中止；不回退其他俄语地区仓，不操作成都，不调用 `warehouse-clear`。已有预览或底层结果出现其他仓库 ID 时不得提交。
- 当前 WB 凭证由用户人工登录、手动抓包并写入，或用 `cookies-update` 导入人工保存的 fetch 文本。Playwright 尚未启动、自动登录/自动续期未启用，不因报错自行安装、启动浏览器刷新或假定会自动续期。
- 受限浏览器进入 Network、复制完整 Cookie 和匹配店铺的步骤见 [手动抓包说明](CONFIGURATION.md#手动抓包更新凭证当前方式)。日志中保留的备用仓/浏览器刷新建议不能覆盖这些现行约束。

## 选择与执行命令

| 用户意图 | 入口与注意事项 |
| --- | --- |
| 看价格/库存修改范围 | price / stock 不加 --apply；先限定 --shops 和商品条件 |
| 商品运营综合报告 | product-report；默认低评分、高退货率及近期出单筛选，完整VC单行，按最长数字段列本店缺口；--details追加证据，不触发同步；先读 [报告说明](PRODUCT_REPORT.md) |
| 提交明确的修改 | 对应命令加 --apply，必要时 --yes；保持授权范围，不改成全部店铺 |
| 获取最新商品快照 | 用户明确要求后独立 fetch；默认 BCS 快照（先同步再读 BASE 缓存，已在后台同步过可用 --no-sync）；需更新映射时再独立 merge |
| 核对归属/中文名 | mapping、review、mapping-check、mismatch-check；本地结果通过对应导入命令处理 |
| 导入/复制上架 | publish、create-cards、replicate、import-publish；核对库存默认值、VC 语义和目标店 |
| 备用官方上架/跨店内容同步 | 显式 publish-openapi / sync-cards-openapi；BCS 默认入口不变；上架含建卡后有限标识等待、图片/莫斯科库存；超时用 publish-openapi --resume 续办，未知写入状态不重放；见 [专项说明](OPEN_API_LISTINGS.md) |
| 处理新订单 | mabang-process；默认配置店铺的全部新增待处理订单，不限日期；不要跳过匹配失败或预报等待直接交运 |
| 发货群供货和标签 | 独立 fbs-group-ship-openapi；逐店莫斯科仓，只处理价格表标记「在发货群发货」的 FBS 新增订单；加 --apply 才创建供货及导出，配送已受理后可用 --resume --apply 补 PDF |
| 查询客服/生成草稿 | questions、chats 或 watch 的 front/back 模式，不擅自添加 --apply |
| 自动回复/定时写入 | 必须有明确自动运行范围；注册任务前说明其时间、全部店铺范围和持续写入性质 |

用户要求为商品报告临时引入其他BCS账号时，使用 `product-report --extra-bcs-stdin`，将本次提供的完整fetch文本通过子进程标准输入管道以UTF-8传入并关闭输入流；多个fetch块依次传入。不要将秘密拼进命令行、环境变量或保存到临时脚本/抓包文件，不运行cookies-update、不替换本机凭证。解析只提取认证，不执行原fetch。`--shops`只筛本机目标，临时账号的全部店铺补充统计且不进入链接缺口目标；飞书仍读取本机一份来源。查看报告中的账号来源及失败明细，凭证失效不启用浏览器续期。详见 [报告说明](PRODUCT_REPORT.md#临时引入其他bcs账号)。

马帮命令默认 `--days 0`，查询新增待处理状态且不发送日期限制，仅处理 `mabang.shop_map` 配置店铺。用户说“处理马帮订单”时不自行缩小为最近1天；正数天数用于明确的最近 N 天范围。分页超限或不完整会中止，不以部分清单宣称全部处理。其他店铺与历史已完成订单不进入匹配、预报或交运。

已配置自动续期的马帮命令可在预览或执行时更新本地会话。遇到验证码或短信验证时停止，提示用户人工登录并用 `mabang-login --from-har` 导入；不读取或输出账号密码，不把认证失败当成无订单、模板缺失或普通逐单失败。已发出的业务写请求不因续期重放。见 [马帮配置](CONFIGURATION.md#马帮mabang)。

复制上架使用 `replicate --source-shops ... --shops ...`，按完整 VC 合并源店，保留完整 VC 建卡。`--price-source minimum --price-multiplier 10` 表示商品价格表「最低售价」×10，保留到分；默认库存999，显式0不替换。默认商品清单与查重读取本地快照和提交记录，缺快照不当作空店；快照滞后时结合已受理的下架/上架回执处理范围。回收站已有卡不会自动恢复，需先区分恢复与新建；不把 BCS 缓存命中直接视为实时状态。整批详情和目标莫斯科仓必须在首个写请求前准备好。

使用已有帮助解决语法问题，不通过执行写入命令“试参数”。dry-run 可以联网和生成本地记录；cookies-update、mapping-rename、merge 等本地写操作不受 --apply 控制。

库存归零与移回收站默认依据本地映射和商品快照定位商品/规格，不为每次操作全量读取远端商品或库存。仓库确认是独立的小范围读取；需要更新快照时按用户要求独立运行 fetch/merge。`trash` 已包含先清库存步骤，无需先另跑 stock；任一规格缺失或清零受理失败时阻止该商品，其他完整商品可继续，非零退出和日志中的被阻止项必须如实汇报。

用户已经明确授权执行的操作，可按现有命令要求完成，不人为增加反复确认。`--yes` 只表示跳过命令自带确认，不能替代任务授权，也不能保证每个破坏性操作都需要这个参数。

`fetch` 的默认 BCS 快照来源会先触发 WB → BCS 同步（加 `--no-sync` 才跳过并直接读上次同步结果），再按 BASE 读取该店缓存；同步失败不中止本次拉取，按原流程打印警示后继续读旧缓存。显式 `--source wb-openapi` 才改用官方接口，该来源不使用 WB 后台 Cookie；缺 apiKey、401/403、限流或读取失败时保留旧快照并报告失败，不自动改回 `--source bcs`，官方令牌应在 BCS 对应店铺更新。两种来源都不补零缺失的价格或库存，分页不完整不能宣称已完成全量快照。

BCS 商品读取先校验原始响应数量，再对同店相同 nmId 和完整 VC 去重；只在非空业务值一致且存在完整原行时保留该整行。快照数量和单店表均按去重结果统计，零值不视为空。标识或业务值冲突时不能手工随意删行、按最新时间覆盖或把失败当空店继续 merge；按 [数据契约](DATA.md#映射快照与标识) 处理。旧快照不会因代码升级自动清理，离线整理前先备份。

## 写操作结束规则

用户要求纠正历史 VC 前缀时使用 `normalize-vc-openapi`：按已有明确归属取价格表前缀，默认预览，`--apply` 才提交；省略 `--shops` 覆盖 BCS 全部店铺，`--vc/--name/--all` 三选一。不得按随机前缀或标题猜商品。只修改前缀不一致的商品，保留原有数字和其他尾部字符；新码冲突时才在末尾追加跨店一致的正整数避重序号，不改写原尾号。任一店商品/回收站读取失败整轮停止；保留 `data/logs/normalize-vc-openapi_*.json` 防止重放，不删除日志绕过已受理/未知/提交中状态。不增加旧新码兼容，不修改本地映射/快照/归属，旧码订单衔接由用户另行维护。完整规则见 [规范化说明](OPEN_API_LISTINGS.md#历史-vc-前缀规范化)。

WB、BCS 写入均异步处理，BCS 还需先同步再查询更新结果，耗时较长。提交并记录本次返回后立即结束：

- 不新增结果验证型写后查询，不补 fetch，不补 merge，不触发全量同步。`publish-openapi` 为后续图片/库存取得本店 nmID/chrtID 而进行的有限 VC/条码轮询属于必要上架步骤；取得标识后提交剩余写入，不能扩展成最终结果验证。
- 不把“本地快照仍是旧值”当作失败，也不因此反复提交。
- 不用 WB 通道超时或会话异常作为自动改走 BCS 通道重放同一批的理由。
- 允许并保留业务必需的两阶段请求确认、用户明确要求的价格审核、马帮交运前预报等待。这些不是额外结果验证。
- 用户后来另行明确要求更新/诊断时，作为新的任务使用对应独立命令；不能自行把它解释成每次写入后的固定步骤。

## 根据什么汇报

汇报本次实际处理的范围、成功/失败/跳过数量、平台返回任务号和本地结果文件。将“提交已接受”与“最终生效”分开描述；不进行实时回读验证来补足最终状态。

必须阅读本次日志中的成功、失败、跳过和人工待处理项；退出码 0 不能证明平台已最终生效。非零退出也可能已有部分提交，不能因此盲目重放整批。持续监听会记录本轮异常并继续，单轮 --once 遇到失败则退出。没有执行过的步骤不能声称完成；失败时说明停在匹配、预报、交运、登记还是其他具体阶段。

商品批量操作默认按动作检查必要字段，已有本店商品缺少必要标识时可在提交前通过官方令牌定向补齐，仅用于内存计划；这不授权额外fetch/merge或切换写入通道。当前库存未知不会阻止设库存，旧包装尺寸缺失不会阻止设置新尺寸，WB只改折扣不需要原价。补齐后仍不能唯一确认的商品保留阻止项；必须查看并汇报 `data/logs/商品操作跳过_*.csv` 完整清单，不能只依据终端前30条或成功数量认为全量完成。

发现令牌/会话错误时，停止该店操作，按 [手动抓包说明](CONFIGURATION.md#手动抓包更新凭证当前方式) 和 [排错说明](TROUBLESHOOTING.md) 更新用户数据区的凭证，不把整份 credentials.json、Cookie、抓包或浏览器资料输出到聊天或提交到 Git。请求维护者协助时只提供脱敏后的命令、错误和计数。

## 常见禁止误用

- 把 daily check 当成只读：它在 --apply 时会修改折扣。
- 把 schedule 预览中的店铺范围当成某次手动 daily 的范围：内置计划任务默认覆盖全部可用店铺。
- 把 --mode back 当成已发送：它只生成草稿，发送还需 --apply。
- 把 ai-test 当成离线测试：它会调用真实 LLM。
- 清空 state 来“重置重跑”：可能丢失去重、纠偏和提交记录。
- 用新数据覆盖用户的生产 data，或在代码更新时把本地数据打包公开。
