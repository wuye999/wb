# 数据文件与业务契约

数据根目录由 [paths.py](../src/sellerops/settings/paths.py) 统一定义。用户数据可整体放入项目根目录的 `data/`；文件名、表头、商品编码和凭证结构遵守下文契约。

## 目录与所有权

| 路径（相对 data） | 用途 | 谁维护 |
| --- | --- | --- |
| `credentials.json` | BCS、WB、马帮、飞书和 AI 配置 | 用户；当前 WB 三件套由人工抓包填写或导入 |
| `商品价格表.xlsx` | 商品名、卖家 SKU、目标售价、包装、前缀、库存 SKU | 用户，是商品主数据 |
| `价格映射表.xlsx` | vendorCode 与中文商品的映射、店铺信息 | merge 等本地命令生成/更新 |
| `products/shop<ID>_products_all.json` | 店铺快照 | fetch 生成；业务读取时可能滞后 |
| `shops/shop_<ID>_<名称>.xlsx` | 各店独立映射 | shops-mapping、merge 等维护 |
| `shops/_archive/` | 停用店铺映射 | 用户归档；聚合会跳过归档店铺 |
| `state/` | 已知归属、纠偏、排除、提交记录、客服去重等 | 业务程序；保留原状态以避免重复处理 |
| `workbench/` | 本地 HTML 工作台 | mapping、review、核查命令生成 |
| `logs/` | 结果 CSV、报表和运行日志 | 各业务命令生成，按终端打印路径查看 |
| `har/` | 用户自己的抓包/会话输入 | 用户，不纳入公开仓库 |
| `wb_browser_profiles/<ID>/` | 保留的浏览器持久化登录资料 | 当前 Playwright 未启动；保留资料不代表自动续期已启用，复制时关闭占用它的浏览器 |
| `ai_test_qa.json` | 本地 AI 对照样例集 | 用户；格式见下文 |

普通用户可维护这些自己的数据。项目源码与说明文档按 [使用边界](../AGENTS.md) 保持只读，临时脚本放项目根目录的 `_scratch/`。

`product-report` 在 `logs/` 生成商品运营工作簿，只读现有快照、归属和提交记录，不覆盖这些数据。BCS提供对应店铺官方令牌，无需新增凭证段；来源链接、UTC+8日期及未知数据约定见 [报告说明](PRODUCT_REPORT.md)。

## 商品价格表

主要读取点使用工作表名 `Sheet1`，第 1 行是表头；不要随意改工作表名。列按表头名定位，允许调整顺序。通用商品读取至少要求「卖家SKU」「产品中文名」「实际售价」，其他业务还需要对应列。

| 表头 | 用途/格式 |
| --- | --- |
| 卖家SKU | 主数据里的卖家 SKU，保持稳定 |
| 产品中文名 | 中文商品名，匹配价格、尺寸和库存 SKU |
| 实际售价 | 数值或可解析公式；店铺整数价通常取向下取整 |
| 产品图片 | 图片信息，部分工作台/报表使用 |
| 尺寸 | `长*宽*高/毛重`，例如 `10*20*30/0.5`；尺寸 cm、重量 kg |
| 最低售价 | 本地价格/包装相关业务参考列，不是所有命令的目标价 |
| vendorCode前缀码 | 4 位商品前缀，如 `TEST`，用于识别同一产品 |
| 库存SKU | 马帮匹配和飞书登记使用；不同于 vendorCode |

「实际售价」只认此列名，不要使用「双倍售价」等其他表头，否则可能报错或告警并留空。

公式解析支持有限的单元格引用、四则运算、括号、数字及 ROUND 外壳，复杂 Excel 函数会回退到文件内保存的计算缓存。openpyxl 不会替你重新计算 Excel：修改复杂公式后，需用表格软件重算并保存。仍取不到结果的商品会告警或跳过，不应随意补零继续改价。

实现：[表头定义](../src/sellerops/persistence/headers.py)、[价格读取](../src/sellerops/persistence/price_book.py)、[映射仓储](../src/sellerops/persistence/mappings.py)。

## 映射、快照与标识

- `vendorCode` / VC：供应商商品编码，常见格式 `BCS-TEST-123456789`。也支持 `ozon-card-`、斜杠尾段和多变体序号等格式。
- `nmId` / `nmID`：WB 商品码。同一商品在不同店铺可能有不同码，不能把主店码直接当作所有店铺的码。
- `chrtId`：库存规格标识，库存修改依赖它，不能用 nmId 替代。
- 库存 SKU：马帮实际匹配的库存编码，从价格表读取，不等同于 VC 或 WB 商品码。
- 当前凡涉及仓库的操作仅允许该店的莫斯科仓库 ID，不跨店复用，不回退成都或其他地区仓。WB 仓库列表取响应 `id`；同一响应中的 `warehouseId` 是另一套 office 标识，开发时不要互换。原始快照中即使含其他仓库，也不代表这些 ID 获得操作授权。

快照通常为 JSON 对象，含 `shopId`、`total`、`rows` 等信息。保留原封装与字段；业务会过滤已经有 `trashedAt` 的商品。`state/多店铺同步状态.json` 保存店铺元信息；缺少时可从快照文件名扫描店铺。

默认 `fetch` 以 WB Open API 重建非回收站商品快照，文件名和行字段兼容旧 BCS 快照。顶层增加 `source=wb-openapi`、`region=cn`、已确认的 `warehouse.id/name` 和 `warnings` 缺失统计；`fetchMethod/fetchedAt/fetchedCount` 记录采集来源、时间及数量。规格 `sizeList[].chrtId` 来自商品卡，价格按规格 ID 关联；`stockList` 只含本店莫斯科仓。未返回库存记录保持空列表，价格缺失保留 null，不补零；合法零价与零库存原样保留。图片缺失为空字符串。`createAt/updateAt` 来自商品卡创建/更新时间，不使用采集时间替代。状态文件的 `fetched` 记录成功店铺数量，`errors` 记录失败店铺；两类文件均不包含密钥。显式 BCS 来源标记为 `source=bcs`，不隐式迁移旧文件。

BCS 来源保留原始行，但不会将“无规格”解释为零库存：空规格、无效或重复 chrtId，以及任一规格缺少有效库存记录时，单店表、总表与覆盖矩阵的库存留空。无完整规格时，附带的占位价格0也不作为实际售价；有完整规格的真实零价、零库存仍保留，展示的小数价格不截断为整数。库存数量的空值、布尔值、负数、非整数或重复仓库记录均视为未知。总表优先展示主店数据，主店缺失的库存或售价不借用别店填充；主店没有该VC时，使用最小店铺ID的同一条代表记录。BCS 快照 `warnings` 增加规格不完整、库存未知、价格未知的商品数。已有文件不会被后台自动改写，表格更新仍由独立 merge 完成。

映射总表主要工作表为「映射总表」，核心列为「产品中文名」「vendorCode」「实际售价」等。`merge` 会根据本地快照、单店映射和状态池重建总表，不会自动刷新远端数据。

## 关键状态文件

| 文件 | 含义 |
| --- | --- |
| `state/vc_known.json` | 历史已知 VC 归属 |
| `state/vc_override.json` | 人工纠偏，中文名解析中优先使用 |
| `state/vc_excluded.json` | 人工排除记录 |
| `state/复制上架记录.json` | 提交/查重记录，避免反复上架 |
| `state/WB_OpenAPI上架记录.json` | 备用官方建卡的完整 VC/目标店、条码、载荷、莫斯科仓与图片/库存阶段回执；未知状态禁止自动重放 |
| `state/questions_replied.json` / `questions_front_shown.json` | 提问已回复与前台已展示集合 |
| `state/chat_replied.json` / `chat_front_shown.json` | 聊天已回复与前台已展示状态 |

`WB_OpenAPI上架记录.json` 沿用 version=1 与原有条码、图片、库存计划；合并后的命令可直接续办旧的已受理记录。可选 `targetNm` 保存已取得的本店商品码，`wait.attempts/reason` 保存等待进度；标识等待超时仍保持建卡 `status=accepted`，图片与库存都受理后为 `finished`。`stages` 内每阶段分别记录 `submitting/unknown/accepted`；只有未提交或明确受理的阶段允许继续，未知提交状态不会自动重放。

不要为了“重新试一次”清空状态文件。损坏 JSON 会明确报错，应从备份恢复或由维护者定位；不要替换成空对象掩盖问题。`.lock` 文件是操作系统锁的载体，可以长期存在，文件存在不代表锁仍被占用，不按时间强删。

## 工作台与批量输入

HTML 工作台在浏览器中人工核对后导出 JSON，再传给对应导入命令。默认 `mapping` 和 `review` 导出的 VC 中心审核结果交给 `merge 文件.json`；单店格式工作台结果用 `mapping-import`。两种导入协议不同，不要混用或随意重写导出字段。

`mapping-rename --file` 接受 `[{"vc":"BCS-TEST-123456789","cn":"新中文名"}]` 形式的 JSON，会修改本地归属和相关映射文件，没有 `--apply` 开关。

`publish/create-cards --file` 支持 `.txt`、`.json`、`.csv`。纯文本每行一个商品码；JSON 可为商品码数组或带 `nmId`（也识别 `sku` / `nm`）的对象数组，参考 [发布样例](../examples/publish.example.json)。CSV 既有普通解析，也有根据中文名/VC 联动价格表推导的分支；带 `nmId` 与 VC/中文名列时可能采用价格表中的价格与尺寸，不要假设 CSV 的 price 总能覆盖主数据。明确覆盖参数时优先使用 JSON 并检查预览。

`import-publish` 则读取另一份 Excel 映射表，按自己的商品价格表与目标店铺做差集；不是上述批量文件的同一种输入。

## 飞书业务表

程序按以下列名读写，目标表必须事先存在，列类型须允许相应值：

| 表 | 主要列与约定 |
| --- | --- |
| 订单登记 | `订单编号`（去重键）、`日期`（付款时间）、`店铺`（多选标签列表）、`BCS编号`、`商品中文名`、`库存SKU`、`wb编号`、`商品链接`、`订单量` |
| 马帮库存登记表 | `库存SKU`、`商品中文名`、`库存总量`、`状态`、图片附件列 `图`（也识别图片/图片附件或附件类型列）、日期列、`总新增订单量` |

订单登记中的库存 SKU 来自本地价格表，缺失时允许留空；wb编号来自下单店铺自己的快照。登记会完整分页读取现有订单编号去重；已有重复不会由普通登记自动清理，单独使用 `feishu-register-dedup`。

`mabang-stock-register --apply` 会先删除库存表已有记录再全量写入，原日期列对应的历史数据不能因此自动保留。`mabang-stock-daily` 的显式日期/区间模式会删除早于起始日期的旧日期列；默认模式和区间模式不能当作同一动作。

## AI 对照样例集

`ai_test_qa.json` 是对象数组，每项有 `question`、`human_answer`、`product`。product 的 cn、title、brand、colors、price、description、options 按字符串提供。可参考 [问答样例](../examples/ai_test_qa.example.json)。`ai-test` 会调用真实 LLM，不是离线单元测试。

## 备份与更新

更新代码或复制生产数据前，停止正在写同一目录的任务和监听进程；需要备份浏览器资料时关闭对应浏览器。备份完整 data，同时保留状态池和会话资料。新旧目录中的 data 是独立副本，不会自动互相同步。

收到发布更新时，保留自己的 data，不要用作者或其他用户的数据覆盖。data、临时副本、抓包、会话、日志由 Git 规则排除；仅不含敏感信息的说明与 `examples/` 样例可提交。
